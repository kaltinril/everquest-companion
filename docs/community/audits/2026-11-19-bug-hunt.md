# Bug hunt across the app (2026-11-19)

The owner, after the issue sweep of the same day: "Have agents of different types (haiku sonnet opus
fable) do a big hunt review for other issues in our code, logic issues, code issues, intention for
the feature issues. Fix things that you validate are real. Make sure we continue to add unit tests
for things." This file is the record: what was looked at, what was confirmed, what was fixed, what
was left and why, and what was refuted (so it is not reported again without new evidence). The rules
each fix left in force are in `agent/BRANCH_NOTES.md` ("Bug hunt 2026-11-19" and the feature
sections); what was asked is in each area's `requirements/` file.

## How it was run

- Two passes. Pass A: the seven changes made that day (the issue sweep). Pass B: eighteen feature
  areas of the whole app.
- Finders were spread over four models (Haiku, Sonnet, Opus, Fable): two on different models for
  each change of pass A; one or two for each area of pass B (the tables name them). Each was told
  what the feature is for (`requirements/`, `BRANCH_NOTES.md`) and to skip decided limits. A finding
  is a concrete scenario with the lines that produce it.
- Every finding was then judged by a skeptic on another model, told to refute it by reading the
  code. Only what survived was fixed.
- Fixes: one worktree and branch per area, a unit test that failed before each fix, then an
  independent review on Opus, then corrections. Engine (Rust) areas ran in two lanes with one cargo
  target directory each (the shared-target trap in `agent/WORKFLOW.md`).
- Not fixed on purpose: anything that narrows a promise, deletes a file of the player's, changes an
  on-disk or protocol format, or is a choice between two defensible rules. Those are listed below
  with the reason; the ones that need the owner's word say so.
- Wiki-data complaints were not in scope (owner ruling of the same day: reported, not fixed).
